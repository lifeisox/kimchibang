# 엑셀 가져오기

최초 자료 이전은 **엑셀 가져오기 → 파일 선택 → 파일 분석하기 → 저장할 내용 확인하기 → 백업 후 기존 자료 삭제·가져오기** 순서로 진행합니다. 마지막 실행 버튼 전까지 업무 자료는 변경하지 않습니다. 실제 실행은 기존 고객·주문·입금·이전 가져오기 내역을 모두 삭제한 뒤 선택한 엑셀로 다시 채웁니다. 계정·비밀번호·로고·판매 제품과 가격 설정은 유지합니다. 삭제 전 전체 DB를 백업하며 삭제와 저장을 하나의 트랜잭션으로 처리합니다. 실패하면 기존 업무자료가 복구됩니다. 삭제 확인과 저장 확인을 모두 선택해야 합니다.

## 현재 승인한 분류 기준

- 할인액의 -$5는 배송비 $5입니다. 나머지 음수는 모두 기타수입이며 판매금액에 중복 가산하지 않습니다. 이전 김밥·초과 입금 구분보다 이번 지시를 우선합니다.
- 이름에 대사관이 있는 기관은 단체/기관으로, 원본 닉네임의 사람 이름은 담당자로 저장합니다. 나머지 개인은 개인으로 보존하며 대사관 소속이 표시된 닉네임은 ‘대사관 이름’으로 구분합니다. 동명이인을 자동 병합하지 않습니다.
- 현재 판매 목록에 없는 과거 제품은 비활성 **기타** 제품에 연결합니다. 주문 원본의 약자·단가·수량·용량 정보는 원본 스냅샷에 보존하며 당시 단가로 저장합니다. 판매 목록의 가격을 과거 주문에 새로 적용하지 않습니다.
- 제품 수량이 없는 행은 제외합니다. 원본과 제외 사유는 가져오기 이력에 보존합니다. 잘못된 숫자는 없는 수량으로 취급하지 않습니다.
- 시트 연도 차이는 확인 대기에서 제외하며 통계는 실제 주문 날짜를 사용합니다.
- 이전에 확인한 열무김치 3.2kg, 맛김치 5kg, 백포기김치 5kg 기준은 유지합니다. 오이김치 등 알 수 없는 용량은 추정하지 않습니다.
- 최초 첨부 원본에만 적용하는 24!52의 수량·금액 $25 정정은 원본 보존과 함께 유지합니다. 다른 파일의 같은 행에 정정을 무조건 복사하지 않습니다.

최초 첨부 원본을 시험 DB에 가져온 결과는 고객 193명·주문 946건·제외 2행, 판매금액 $77,350 + 배송비 $235 + 기타수입 $262 = $77,847입니다. 입금 완료 표시는 $77,747, 미입금은 2건 $100입니다. 날짜 없는 과거 입금에 주문 날짜를 대신 넣지 않습니다.

## 개발용 메뉴와 최종 운영 메뉴

Codespaces 개발·테스트에서는 가져오기 후에도 메뉴를 유지합니다. 새로 준비한 가져오기는 같은 파일이든 다른 파일이든 기존 업무자료를 교체합니다. 증분 비교·부분 합치기는 하지 않습니다. 같은 실행 화면의 중복 전송은 한 번만 처리하며, 준비 후 자료가 변경되면 삭제 전에 중단하고 다시 준비하게 합니다. 빈 자료·확인 대기·보류가 있는 자료로는 초기화할 수 없습니다.

Hostinger 최종 배포에서는 서버 환경 변수 `APP_HIDE_IMPORT_AFTER_COMPLETE=1`을 설정합니다. 이 설정이 켜져 있고 보류 없이 주문을 실제 가져온 이력이 있을 때 메뉴를 숨기고 추가 가져오기 요청도 차단합니다. 개발 환경에서는 이 옵션을 켜지 않습니다.

코드 업데이트 자체는 기존 업무자료를 삭제하지 않습니다. 가져오기 화면에서 삭제 범위와 새 자료를 확인하고 실제 실행할 때만 초기화합니다. 이전 가져오기 DB 기록은 삭제하지만 복구용 백업 파일과 비공개 원본 파일은 보존합니다.

## 보존·백업

실행 전 전체 DB 백업은 웹 루트 밖 `.local/import-backups/`에 권한 0600으로 저장하며 실행 기록에 파일명과 SHA-256을 남깁니다. 오류는 한 트랜잭션으로 롤백하고 백업은 보존합니다. 고객·주문 쓰기와 가져오기는 DB별 잠금으로 직렬화합니다. 가져온 주문의 원래 제품·가격·금액과 원본 스냅샷은 보존합니다. 미전달 제품의 전달 처리와 미입금 대금의 입금 처리는 주문 상세에서 각각 추가할 수 있습니다. 선입금 후 전달도 가능합니다. 이미 완료된 전달·입금은 다시 입력할 수 없으며 원본 주문의 수정·취소는 제한합니다. 이 기능은 기존 가져오기 주문에도 적용되므로 다시 가져올 필요가 없습니다.

복원 도구는 `scripts/restore-import.php`입니다. 사용자 명시적 복원 요청 후 현재 DB와 일치하는 백업으로 수행하며, 복원 직전에도 안전 백업을 만듭니다. SQL 복원은 유지보수 중 진행합니다. 고객 자료·백업·비밀번호는 Git에 넣지 않습니다.


## 고객 수령 방법과 지역

고객명단 H `배달여부`가 교회이면 교회, 픽업이면 직접 픽업으로 저장합니다. 이 명시적 표시를 우선하고 그 외에는 주소가 있으면 집으로 배달, 없으면 직접 픽업으로 저장합니다. 주소나 H의 다른 메모를 이용해 실제 과거 주문의 수령 방식을 추정해 바꾸지는 않습니다. 이번 분류는 앞으로 주문을 만들 때 사용하는 고객 기본값입니다.

주소의 명확한 지역명을 우선 사용하며 도로 이름을 지역명으로 판단하지 않도록 구분합니다. Nepean처럼 넓은 우편 지역 표기는 D의 구체적 지역을 덮어쓰지 않습니다. 주소에서 알 수 없으면 D 대응표를 사용합니다: 센터→Carlington, 바헤븐→Barrhaven, 스팇빌→Stittsville, 대사관·다운타운→Downtown, 핀들레→Findlay, 올리즈·올린즈→East, 카나다·카나타→Kanata, 교회·픽업·기타→Etc, 칼링→Carlington, 나머지→Etc. 사용자 입력의 Calrinton/Sttitsville은 목록의 Carlington/Stittsville로 통일합니다. 유료 API나 외부 주소 전송은 사용하지 않습니다.

이전 분석 결과에 H열이 없으면 원본 파일을 다시 선택해 분석해야 합니다. 원본이 비공개 경로에 남아 있으면 자동 재분석하고, 새 업로드 원본도 `.local/imports/source-{sha256}.zip`에 비공개로 보관해 다음 분석에 사용합니다. 원래 지역·H 값과 분류 근거는 고객 가져오기 원본 기록에 보존합니다.
