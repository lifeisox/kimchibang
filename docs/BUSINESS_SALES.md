# Rodem Namu 판매 관리 개발판

판매 관리 → 김치방 → 기장 메뉴 순서이며 개발 환경에서만 켭니다. 현재 Hostinger 판매·기장 배포판에는 새 판매 관리 코드와 제품 자료를 포함하지 않습니다. 기존 판매/기장 거래를 변경하거나 Geeland 기록을 지우지 않습니다. 새 판매 관리에는 Geeland와 Cheese 제품을 등록하지 않습니다.

## 시작

`codex/business-sales` 브랜치를 갱신한 기존 Codespace에서 다음을 실행합니다.

```sh
php scripts/enable-business-preview.php
sh scripts/cloud-start.sh
```

미리보기 표시는 현재 DB에만 적용되며 운영 배포판에서는 켜지지 않습니다. 기존 DB와 계정을 보존하고 별도 `biz_` 테이블을 추가합니다.

1. 거래처·발신 정보에서 사업자 주소/GST 번호와 세 거래처의 주소/이메일, 개인 고객을 입력합니다.
2. 제품·단가에서 정가와 거래처별 납품가를 입력합니다. 정가는 빈 값으로 시작합니다. 김치방/생산 전용 기존 제품과 별도 관리합니다.
3. 생산·납품 계획에서 다음 날 거래처별 수량과 개인 판매의 픽업/배달, 할인율을 입력합니다.
4. 생산량에서 날짜별 전체 제품 수량과 확인된 재료 소요량을 보고 인쇄합니다.
5. 실제 납품 수량을 확인합니다. 직매출은 같은 계획의 직매출 제품 납품이 모두 끝나면 하나의 인보이스가 발행됩니다. 위탁품은 매출로 잡지 않습니다.
6. 실판매·반품에서 판매 수량과 포함된 직원 수량, 반품/폐기를 추가 입력합니다. 남은 재고를 넘을 수 없습니다. 0개 판매일도 마감합니다. 재고가 남으면 다음 날에도 같은 납품 건에 추가 판매를 기록합니다.
7. 정산·인보이스에서 기간을 선택해 위탁판매분을 발행합니다. 인보이스는 한영 제품명, 당시 단가/할인/세금/발신 정보의 스냅샷을 보존합니다.
8. 현금/eTransfer 수금은 인보이스별로 기록하며 분할 수금과 잔액을 관리합니다.

## 거래처 규칙

- OK Mart: 김치는 납품가로 즉시 직매출. 김밥·삼각김밥·주먹밥은 정가 기준 위탁. 실제 판매의 품목별 합산 금액에 20% 할인 후 HST 13%. 전주 월~일 정산.
- Popularitea: 김치는 납품 즉시 판매로 기록하되 청구는 삼각김밥 실판매와 함께 월 단위로 합니다. 나머지 위탁품은 실판매만 기록합니다. 전 품목 거래처 납품가. 직원 수량은 우선 전체 판매 수량에 포함된 것으로 구현합니다. 직원 할인율은 사용자가 등록해야 하며 미등록 시 직원 판매 정산을 막습니다. 현재 월 정산일은 수동으로 고릅니다. 자동 발송일과 직원 수량 포함 여부는 사용자 확인 후 확정합니다.
- Hungry Ninja: 납품 수량이 판매 수량이며 납품가 적용. 현금 수금은 사용자가 별도로 확인/기록합니다. 자동으로 입금 완료로 만들지 않습니다.
- 개인: 정가와 건별 할인율. 수량/픽업에 따른 자동 할인 기준은 아직 정해지지 않아 직접 입력합니다.
- 김치는 HST 0%, 나머지는 13%. 모든 금액은 정수 센트로 저장합니다. 합산 할인/세금을 반올림하고 센트 잔차를 배분합니다.

정산한 기간의 추가 위탁판매, 과다 판매/반품, 초과 수금, 동일 기간 재발행, 중복 제출을 차단합니다. 발행 후 반품/취소/환불/수금 정정용 Credit Note는 다음 단계이며 현재 잠긴 기록을 직접 수정하지 않습니다. 생산 예정 수량 수정/취소 UI도 다음 단계입니다. 현재 버전은 개발 시험용입니다.

## 생산 기준

엑셀 ‘생산량’ 시트의 확인 가능한 김밥·기본 삼각김밥 재료 공식을 옮겼습니다. 쌀/계란은 부족하지 않게 올림합니다. 주먹밥과 추가 맛의 전용 배합은 확인되지 않아 ‘배합 확인 필요’로 표시합니다. 삼각김밥 배합을 주먹밥에 임의로 적용하지 않습니다. 김치는 기존에 등록된 주재료 배합을 읽어 새 판매 규격의 무게로 계산하며, 기존 김치방 생산계획의 배합/마트 제품은 변경하지 않습니다. 재료 준비표는 완성된 전 제품 배합표가 아닙니다.

## 이메일과 자동 정산

`scripts/business-cron.php`의 기본 실행은 점검만 합니다. `--run`은 월요일 오타와 시간 08:00 이후 전주 정산을 확인하며, 해당 기간 재고가 있었던 모든 납품 건의 일일 마감이 없으면 발행을 보류합니다. 인보이스는 먼저 수량·금액을 확인하고 발행하세요.

`--run --send`와 운영 설정 `BIZ_MAIL_ENABLED=1`이 함께 있어야 PHP mail()을 호출합니다. 현재는 꺼져 있으며 실제 이메일을 보내지 않았습니다. Hostinger cron 실행 시각, 도메인 발신 이메일·SPF/DKIM·수신 테스트를 마쳐야 자동 발송을 활성화합니다. 발신 설정에는 비밀번호를 채팅에 보내지 않습니다. cron은 오타와 시간으로 판단하므로 호스팅의 UTC/DST 설정과 일치하는지 확인합니다.

OK/PT 인보이스는 발행 시 발송 대기, 다른 거래처는 수동 상태로 시작합니다. 메일은 인보이스를 HTML 본문에 넣으며 PDF 첨부는 아직 아닙니다. 인쇄 화면에서 PDF 저장은 가능합니다. 메일 서버 접수(accepted)와 실제 도착은 구분합니다. 실패·중단된 발송은 도착 여부를 확인한 후 인보이스 화면에서 다시 대기 등록합니다. 중복 메일을 피하기 위해 sending 상태는 자동 재발송하지 않습니다.

## 첨부 엑셀 분석 범위

OK DAT, PT DAT, NJ DAT, 각 계획/결과, 생산량, 배합표, CUSTOMERS, 인보이스 양식을 확인했습니다. 파일에 2024/2025 기록과 현재 제품 목록에 없는 과거 규격, Cheese, 50% 할인용 열이 섞여 있습니다. 과거 거래는 아직 DB에 가져오지 않았습니다. 이전 단가를 현재 단가로 임의 등록하지 않습니다. 과거 데이터 가져오기는 규격·판매/납품·기간을 검토한 별도 단계로 진행합니다. 원본 엑셀은 비공개로 보관하며 Git에 넣지 않습니다.

## 검증

`python tests/business.py`는 임시 DB와 HTTP/브라우저에서 메뉴 순서, 제품 31종, 위탁/직매출, 재고 제한, 정산, 직원 할인, HST, 이중 발행, 수금, 모바일/PC, 최대 품목 인보이스 A4 한 페이지를 확인합니다. 실제 이메일은 보내지 않습니다.
